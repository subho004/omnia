# Requirements and login flow

## v0 behavior

- A user requests an instance; the service creates that user's dedicated container and persistent named volume.
- The instance UUID is generated by the server. Its volume is named `openclaw-data-{uuid}`. The owner approved native OpenShell Docker container names; keep the full UUID and actual container identity in orchestrator metadata.
- Each demo identity has at most one active instance. Repeated requests return the same resource; they do not generate a new UUID or volume.
- `user1` and `user2` can run concurrently without sharing data, configuration, credentials, browser origin, or tenant network.
- Every browser/API request to OpenClaw goes through authentication and owner authorization, including files, plugins, assets, streaming responses, and WebSockets.
- User2 cannot retrieve user1's data by changing a UUID, hostname, path, header, cookie payload, or upstream address. UUID secrecy is not a protection.
- OpenClaw uses its normal paths at `/` on the selected instance hostname. No instance UUID path, JWT query parameter, or direct backend port is exposed.
- Data remains after restart and container recreation. Replacement is a later operator workflow, not another v0 user API.
- The orchestrator's own database is PostgreSQL in Docker Compose. Persist its files under this repository's gitignored `db/` directory using a bind mount, separate from tenant named volumes.

## Login page: exact button order

Signed out:

```text
[ User1 ]
[ User2 ]
```

Signed in as user1:

```text
[ Visit OpenClaw ]
[ Switch to user2 ]
[ Logout ]
```

Signed in as user2:

```text
[ Visit OpenClaw ]
[ Switch to user1 ]
[ Logout ]
```

Login and switching are POST actions. The server signs a JWT and sets an HttpOnly cookie; browser JavaScript never constructs or reads it. Render the active identity clearly. Switching replaces the login session and revokes the old session's proxy grants and live streams.

“Visit OpenClaw” submits an authenticated, CSRF-protected POST. It creates the instance if absent, shows a provisioning state while waiting, then performs a one-use launch exchange to the user's instance origin. Once ready, the final browser URL is `/` on that origin. No separate create button is required. Disable repeat submissions while a request is outstanding, while retaining server-side idempotency.

Show `Preparing instance…` and bounded retry/status polling during creation. Failures show a safe error and request ID; they must not offer another user's instance or create unlimited replacements. Returning to the login page re-reads the session server-side.

## Scope limits

Only local, explicit demo identities exist. Anyone with access to the enabled demo selector can intentionally select either identity; this is useful for testing authorization, not production authentication. Production identity proof, registration, account recovery, external sharing, fleet scheduling, deletion, billing, and zero-downtime upgrades are outside v0.

The host administrator, Docker daemon, orchestrator, and OpenShell control plane are trusted. The isolation goal is protection against another authenticated tenant and its workload under the configured sandbox controls. It is not a claim that a shared kernel withstands every exploit. Previously displayed/downloaded content and a person controlling the same browser profile cannot be made secret retroactively by logging out. Acceptance tests verify new access, streams, and cross-origin storage separation.

## Assumptions

- One host, two seeded users, one stable instance per user, one orchestrator worker.
- Docker Desktop or an equivalent supported runtime is already available for later integration work; no GPU or local model is assumed.
- Use the owner-selected LM Studio OpenAI-compatible endpoint on 127.0.0.1:1234 with the loaded qwen/qwen3.5-9b model for the first real smoke test. Keep runtime credentials outside tenant data via supported bindings.
- Local HTTPS, hostname resolution, and certificates are explicit prerequisites; test the browser rather than assuming wildcard `localhost` works everywhere.
- Runtime naming, persistent mounts, network controls, and gateway auth remain feasibility gates. A documentation plan is not evidence that upstream already satisfies them.
